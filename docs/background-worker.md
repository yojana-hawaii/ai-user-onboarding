# Core background worker — WBS 1.7

The worker runs in a separate process using the existing .NET 10 backend image. It does not start HTTP endpoints, OIDC middleware or session services. It registers the core NotificationRetry handler with Mock delivery by default; lifecycle handlers belong to later approval, provisioning and scheduling tasks. See [notification configuration and evidence](notifications.md). All eight schema job types are supported by the dispatcher; a missing, unknown or multiply registered handler fails visibly with `HandlerUnavailable`. The helpdesk choice remains deferred.

Apply `WorkerAttempts` after `InvalidatePermissionKeyChanges` before starting a worker. The migration creates `BackgroundJobAttempts`, keyed by `(JobId, Attempt)`, with UTC start/completion timestamps, outcome, safe error code and retry deadline. The runtime can insert/update attempts but cannot delete them. New jobs default to `MaxAttempts=4`; existing explicitly persisted budgets remain unchanged. No deployment migration is run automatically by the worker. Rolling back drops attempt evidence; archive it before any authorized rollback outside disposable tests.

For an explicitly configured development database, start the separate worker with:

```powershell
docker compose -f compose.yaml -f compose.worker.yaml --profile worker up -d worker
```

This overlay inherits the existing non-root, read-only, capability-dropped backend container and mounts only the development database connection secret. The API does not run the polling loop. No worker starts through the normal development command. Production requires a separate restricted SQL/service identity, approved secret mounts, protected persistent operational logs and monitoring. No AD/Graph/helpdesk credentials or privileged live handlers are provided here.

The worker polls every 60 seconds when idle or storage is unavailable and drains due work sequentially. SQL `UPDATE ... OUTPUT` selects one due row under `UPDLOCK, READPAST, ROWLOCK`, ordered by due time and ID. Claim and attempt insertion commit atomically. Concurrent processes cannot claim the same queued attempt. SQL Server UTC time determines claims, recovery and retry deadlines; no application-clock synchronization is required for those operations. Tests exercise the supported SQL Server 2022 database with its default read-committed isolation configuration; enabling READ_COMMITTED_SNAPSHOT requires revisiting the claim hints.

A handler returns `Retry` only for a known transient failure whose external result is understood. AttemptCount increments at claim, including the initial execution. A new job gets at most four executions: the initial attempt and retries 1, 4 and 16 minutes after the preceding failure. Every outcome and deadline persists. Exhaustion marks the job Failed; completion/failed/cancelled rows remain. The worker never completes or fails the parent request, resets another step, or changes approval/EHR state. Other independent jobs continue after a handler failure.

Handlers have a two-minute execution deadline and must cooperate with cancellation. Shutdown allows up to 15 seconds to persist the outcome independently of the cancelled host token. An exception, cancellation or timeout can follow an external success, so it produces `ReconciliationRequired`, without automatic replay. After five minutes, an abandoned InProgress claim becomes Failed with the same code and retained attempt evidence. A late result cannot finalize a recovered/replaced claim: updates compare job ID, attempt count, InProgress status and StartedAt. This is a database fencing check, not an external-system transaction or an exactly-once guarantee. An uncooperative handler may still have an in-flight external operation; reconcile that result before authorizing replacement work.

Terminal failures emit structured Critical IT-attention events with job ID and attempt number. Recovery emits an aggregate count. With [worker failure destinations configured](notifications.md#worker-failure-alerts), a terminal failure, exhausted retry or abandoned claim commits its outcome, attempt evidence and IT notification jobs in one SQL transaction. The claim fence prevents a late completion from generating a duplicate alert. The notification worker handles delivery separately. Monitor critical events and the durable failure backlog, including unsuccessful notification jobs. Handler diagnostic codes are allowlisted.

## Handler execution contract — WBS 1.7.3

Persist a `JobExecutionIdentity` in the job payload: stable ActionKey, RequestId, immutable Revision, EmploymentPeriodId and approved UTC end time for scheduled/expiry work. An action key identifies the logical side effect, survives retries/replacement jobs and must distinguish different steps, revisions and employment periods. Enqueue within the same transaction as the authoritative workflow mutation. Do not put secrets, patient PHI or raw provider responses in payloads or evidence.

Before each external side effect, the handler must use its `IJobExecutionAuthority` implementation to re-read current request revision, approval or immutable urgent authority, cancellation state, employment-period/account binding and exact approved schedule. Recheck current actor permissions where execution depends on an actor's authority. A stale/rejected/superseded/cancelled or old-period operation returns Cancelled with `StaleExecution`; unavailable authority fails closed. Pending extensions must not replace the approved end time. Validate that payload RequestId and step associations match the persisted job and authoritative request. Job payloads are references, not proof of authority.

Use `IJobResultReconciler` to inspect the external system by the same action key and stable external identifiers before retries. `JobExternalResult` distinguishes Absent, Confirmed and Uncertain and contains only an approved evidence reference and external ID. Confirmed results are reused; an uncertain result requires reconciliation rather than an automatic new write. Provider idempotency keys, durable per-action results and tests for timeout-after-success are mandatory when real handlers are introduced. These interfaces define the integration boundary; they do not implement lifecycle authorization or external reconciliation. No production side-effect handler is registered, and no live directory, license, mailbox or ticket operation was performed.

## Mock provisioning boundary — WBS 1.7.2.2

`ProvisioningStepHandler` and `SqlProvisioningActions` provide a bounded Sprint 3 seam. Neither API nor WorkerHost registers the handler, its authority resolver or a provider. There is no provisioning endpoint, automatic activation, live adapter or provider credential. `IMockProvisioningProvider` supports only synthetic directory/helpdesk operations; the helpdesk vendor decision remains deferred. Missing handler registration still fails visibly.

Apply `MockProvisioningActions` after `NotificationChannels` before using this worker revision: claims now consult that table. The migration adds one durable logical action per step, a case-sensitive unique action key, immutable request/revision/period/initiator/operation/prerequisite binding, job/attempt ownership and bounded result references. SQL enforces identity immutability. Runtime SELECT/INSERT/UPDATE is granted; DELETE is denied. Rolling back removes action evidence. No migration runs automatically; no persistent application database was upgraded for this work.

Sprint 3 must supply the authorized immutable snapshot, real current-authority resolver, initial step selection/dependencies and parent-state aggregation. The seam atomically creates one synthetic step/action/job. It checks request/revision/period and employee-period consistency; the authority contract must validate approval or designated urgent authority, current local permission, cancellation and approved end time. Tests supply synthetic authority, not a production implementation. An action is not authorization. Jobs reference the durable step rather than carry provider requests or authorization in payloads.

This slice permits roots and a single previously created prerequisite per action: independent chains, not the full dependency graph/fan-in planner. Incomplete prerequisites prevent claims without consuming attempts. Independent due jobs continue. Current request, approval, resolution and EHR state are never updated by the worker. Urgent execution does not grant approval; a helpdesk result does not establish EHR fulfillment.

Before provider contact, the handler persists ownership only for a current SQL claim and eligible action. Competing jobs cannot steal an in-flight effect or bypass another job's retry deadline. It reconciles first and rechecks authority immediately before an effect or adopting confirmed evidence. Only known-no-effect transient failures retry, with the existing four-attempt budget and persisted 1/4/16-minute delays. RetryCount counts retries after the initial attempt. Uncertain or abandoned actions require reconciliation without automatic replay.

Step outcome, result evidence, append-only worker audit, job/attempt, retry deadline and applicable alert intent commit in the existing fenced completion/recovery transaction. Handler contexts do not flush domain outcomes independently. Audit identifies the executing service as `DaHub.Worker` and separately records the stable initiating AppUser ID, job and attempt; it does not impersonate that user. Only bounded identifier-like references and allowlisted error codes are retained, never raw responses.

The SQL harness explicitly creates replacement jobs to reconcile recovered actions. They reuse the immutable key and complete only from confirmed prior evidence; absent/uncertain results never replay. No manual retry endpoint is implemented. The fake provider ledger survives application-context replacement and local rollback within the test process; this is not a durable live service or an actual process-crash test. Real-provider idempotency/reconciliation, dependency fan-in, workflow APIs/UI, manual resolution and live outage/IT receipt acceptance remain open. External exactly-once execution is not claimed.
